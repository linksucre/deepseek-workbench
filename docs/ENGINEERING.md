# 开发及合并流程

1. 从 [TASKS](../TASKS.md) 领取工单，注明操作者、负责目录、依赖、测试和预计证据。独立 worktree 中开发。依赖未合并时先做只读检查或标记阻塞。
2. 小幅改动先按现有设计实现。公共接口、持久化、授权、模块边界、兼容性或依赖变化需先开独立设计 PR。说明需求 ID、影响、备选方案、迁移/回滚和验收；维护者批准设计后开始实现。
3. 编写最小必要实现与回归测试。修改源代码时同步相应模块设计或明确记录适配变化。更新契约时同步 API/Data Model 说明与使用者。任务状态实际开始才改 active。
4. 实现 PR 描述问题、变化、任务/需求/验收编号、验证命令与证据。维护者审查依赖、权限、公共影响、异常路径和文档同步。
5. 通过 PR 合并到 main。由不同 Agent 独立技术复核，记录所审提交、发现和测试结果。提交更新后重新核对变更和两项必需检查 `Repository gate` 与 `Harness integration`，由维护者作最终决定并执行合并。GitHub 最少审批人数为 0，禁止绕过检查和直接推送。
6. 合并后移交变更记录和复测证据，更新 TASKS。若回归，按部署手册停用或回退已验证基线，并记录影响及修复工单。

在多人协作时，仓库维护者指定模块负责人。并行任务只能各改自己的目录。跨模块公共改动由独立工单一次提交并评审；其他工作分支更新基线后接入。自动检查可以发现未同步文档和断链，行为一致性由测试和评审判断。
