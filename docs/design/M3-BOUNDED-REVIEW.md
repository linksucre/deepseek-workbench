# M3 独立审阅设计评审

FR-010、DEV-011、TST-010、AC-010。此稿与隔离工作树中的实现供维护者评审。

## 授权与预算

工作台用户在活动 Run 中填写一个问题和明确选择的材料。主 Agent 无法通过工作台工具派发审阅。原生审阅会话从空会话起步，按独立预设运行，模型请求的工具表为空，工具执行另有 Host 拒绝。问题与材料合计最多 24 KiB，每次生成向提供方请求最多 1024 token，120 秒时请求取消并等待原生清理，深度 1。每次 Run 最多派发两次，同时只保留一项待核对审阅。保留 Harness 的提供方、模型和费率配置。

## 持久化与重启

派发前在任务记录中原子写入审阅 ID、预留子会话 ID、Run、请求人和请求回执。请求回执保存输入摘要。选中的材料随本次用户操作交给原生子会话。任务数据库存储问题及审阅摘要。相同请求 ID 重放读取已有状态，首次发送失败或结果未知时，用户通过“核对审阅”读取原生会话，再更新任务记录。核对不派发子会话。

核对同时检查 Run 阶段游标后的父会话目录事件和子会话原生头，包括预留 ID、父会话、工作目录、创建时间及审阅预设。证据不足时保留未完成标记。完成信号及正文取自已验证子会话的第一轮。仅将其归属该 Run 并记录输出截止游标，后续独立使用同一个原生会话产生的用量不计入审阅。

用户可显式将已完成审阅的摘要发送给该 Run 的主 Agent。工作台按当前用户发送摘要，正文附审阅 ID 和核查提示。审阅摘要作为建议供主 Agent 查验，接受交付继续使用现有的原生证据和用户确认。待核对审阅需要先处理才能结束 Run。

## 联调复现与修订提案

在组合候选 `5bd55ef` 上以固定 Harness 和本地模拟模型复现以下三项。修订待维护者评审。已认证的本机 owner、工作区与根会话归属、同源请求、无工具审阅和显式回送沿用原设计。

### 冷根会话的派发预检

任务在 Host 重启后仍为 `active`，但原生根会话尚未加载。连续两次派发各返回 `incomplete`、各增加两个 revision，始终没有子模型请求。用户向主会话发送消息使根会话恢复后，第三次派发因配额已耗尽返回 409。

建议在同一个宿主派发临界区先核对权限、已有回执和输入摘要。原请求重放直接返回当前审阅状态，新请求才检查任务 revision、活动 Run、根会话归属及活跃的原生实例。根会话尚未加载时返回 `INVALID_TRANSITION`（409），提示用户先在原会话继续工作。此分支不写预留、不增加 revision、不计入两次配额。前置条件满足后原子持久化预留和回执，再由 Host 复核同一根会话实例并派发。预留后外部动作结果不明时仍按既有核对路径处理。

备选方案是在用户本次派发授权下，通过宿主能力加载原会话且不发送模型消息。采用该方案需要额外确认宿主授权、加载副作用和恢复失败语义。保留原实现会把已知前置条件失败和已预留的失败尝试都计入配额。

### 核对命令的公开回执

完成 `task.review.reconcile` 后，用同一请求 ID 改查另一个已完成的审阅，会成功返回另一个结果。候选只把 Host 自动结算的内部 ID 写入回执，未记录本次公开操作的请求 ID 和输入摘要。

建议将显式核对与自动结算分别记录。显式核对以任务、操作者、`task.review.reconcile` 和客户端请求 ID 为作用域，摘要覆盖提交的输入，包含审阅 ID 和预期 revision。授权后先查公开回执。同摘要返回核对时保存的结果，即使任务已继续更新。不同摘要返回 `INVALID`。首次成功核对将结论和回执原子写入同一任务记录。核对期间出现 revision 竞争时返回冲突，由用户刷新后确认；内部自动结算仍使用自身回执和恢复逻辑。

早期版本的内部回执不能证明某个公开请求 ID 曾核对哪个审阅。已结算且没有可匹配公开回执时，核对返回 `RECONCILIATION_REQUIRED`，客户端通过 `task.reviews` 读取已有结果。不得反推旧请求或补写旧回执。备选方案是改契约，将核对变成仅按审阅 ID 读取结果，由另一条命令完成结算；这会增加操作面，并改变现有客户端调用。

### 回送命令的原生请求 ID

先以 `review-forward:shared-key` 作为普通 `task.prompt` 的请求 ID 发消息，再以 `shared-key` 作为 `task.review.forward` 的请求 ID 回送，回送返回 `INVALID`。旧回送把前缀拼到客户端 ID 上，再由普通消息路径对任务、Run 和拼接后的 ID 计算原生 ID。相同输入会落到同一原生键。

建议保持普通消息原生 ID 的推导方式。Host 以 `workbench-review-forward-v2-` 加 `[taskId, runId, requestId]` 的摘要作为新回送原生 ID。摘要为 JSON 数组序列化后 UTF-8 字节的 SHA-256 小写十六进制值。客户端只提供公开请求 ID。回送继续走同一原生排队入口。首次新回送为该任务、操作者、操作与公开请求 ID 持久化输入摘要、目标 Run 和原生 ID，收到可信受理回执后标记完成。跨重启核对仍使用这个原生 ID。公开请求已匹配时先复查权限与摘要，同摘要返回已有回执，摘要不同返回 `INVALID`。结果未知时查原生受理记录，证据不足返回 `RECONCILIATION_REQUIRED`，保留原意图供核对。新请求继续要求活动 Run 和当前 revision。

旧服务完全停止后，在恢复工作台写入前，为每个存量 Run 保存根会话已持久化的事件截止游标。核对已受理的原生队列都能从日志或可信回执读取。无法确定旧服务已停止或受理记录完整时，暂缓该 Run 的回送。升级后创建的 Run 只用新作用域。

升级后缺少新回执的请求，只在已授权的同一根会话、同一 Run 的升级截止游标以内查旧原生 ID。游标之后的普通消息归新版本的普通消息操作。旧 ID 的推导仍为 `workbench-<SHA-256([taskId, runId, "review-forward:" + requestId])>`。依据可信原生队列及用户消息事件判断：

- 旧 ID 与当前审阅生成的完整回送正文逐字一致时，返回现有 `accepted: true`，表示相同正文已受理。普通消息也可提交相同正文，历史事件无法区分来源操作，审计记录只保留原生受理事实。可用新的公开回执绑定本次已核对结果，重放时不再排队。
- 旧 ID 存在但正文不同、来源不可验证或仅取得不完整观测时，返回 `RECONCILIATION_REQUIRED`，不为旧请求写入成功回执，也不发送消息。用户可先核对主会话，再显式用新的请求 ID 发起回送。若旧记录经核验仅为普通对话，旧请求继续归原命令所有。
- 只有可信且完整的观测能确认旧 ID 在切换前未受理、未在途时，才可使用新原生 ID 发起排队。旧版与新版服务禁止共用同一 profile 并发写入。

备选方案是重算普通消息的所有原生 ID，需要同时迁移普通对话的历史回执。直接切换到新回送 ID 实施简单，但在旧请求响应丢失后可能重复发送。同一正文的兼容读取加版本化回送 ID 可以保留可验证的历史结果，同时隔离新回送。

## 兼容与回退

公共契约仍为 v1 的四个 owner 操作，修订复用已有错误和响应形状。旧客户端可继续调用现有操作。新增内部回执与切换游标按存储设计评审，旧 V1 记录缺少审阅或新增回执时按空读取。存量 Run 在兼容回送前记录一次切换游标。历史回执和原生会话日志保留原样。上线前停止旧服务，在独立 profile 备份任务记录和原生会话，复核历史普通消息、审阅回送及待核对记录。

回退前停止 Workbench 写入并保留当前 profile 副本。回退到只识别旧回送 ID 或旧任务记录的版本时，从同一升级前备份恢复任务记录与原生会话，复核旧回执后再写入。保留升级期会话作为只读资料时，先完成兼容核对，再恢复回送，以免旧版本重复受理升级期请求。

## 修订验收

使用固定 Harness、独立临时 profile 和本地模拟模型，在 `tests/integration/host-delivery-smoke.mjs` 落实以下 TST-010 回归。核对 HTTP 状态、任务 revision、持久回执、原生排队事件和模型请求数。

| 场景 | 通过条件 |
| --- | --- |
| 先启动任务，再重启 Host，保持原生根会话未加载 | 两次新派发均返回 409 `INVALID_TRANSITION`，审阅记录、revision 和模型请求数不变。用户继续原会话后，仍可完成两次合法派发。已持久化的派发请求在根会话仍冷时可重放，且不会创建子会话。 |
| 子会话完成后，注入任务尚未结算的故障并重启 | 显式核对提交一个公开回执和一次 revision 更新。同 ID 同输入跨重启返回原核对结果。同 ID 改审阅 ID 或预期 revision 返回 `INVALID`，没有新模型请求或状态写入。旧内部回执保留，旧公开身份无法证明时可从列表读取最终状态。 |
| 在升级后的存量 Run 同时调用原本会碰撞的普通消息和新回送请求 ID | 使用两个不同的原生 ID，各受理一次。新回送在原生受理后丢失响应，跨重启重放只返回原受理结果。普通消息的原始 ID 仍可重放。 |
| 以旧候选生成普通消息和回送记录，再用同一 profile 升级 | 同正文旧回送重放返回已受理且无新增消息。旧 ID 有冲突或观测不完整时返回 `RECONCILIATION_REQUIRED`。用户核对后用新 ID 显式回送，可独立受理一次。确认旧 ID 未受理时，首次新回送按新 ID 受理。 |
| 升级及回退独立 profile | 旧记录读取通过，存量任务数、revision、原生会话和旧回执保持一致。恢复升级前备份后验证旧回送和普通消息重放。记录未发布候选期间产生的升级期数据在保留副本中的位置。 |
